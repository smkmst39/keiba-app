# CLAUDE.md 過去の事例（アーカイブ）

`CLAUDE.md` の「過去の事例（教訓）」セクションから移動された古い事例を
ここに保管する。直近10件は `CLAUDE.md` 側で保持、それを超えた分が時系列で
こちらに追加される運用。

## 運用ルール（再掲）

- `CLAUDE.md` 側に直近10件を保持
- 10件を超えたら古い順にこちらへ移動
- 各事例は「日付・タスク名・推測実装の落とし穴・回避できた理由」を1段落でまとめる
- アーカイブされた事例も検索可能。必要なら `grep` でこちらも当たること

## 事例 (古い順)

- **2026-05-07: courseRecord (Phase 1-D)**:
  shutuba_past.html ベースで実装する仕様だったが、下調べで以下が判明:
  - shutuba_past は **着順を持たない**（凡例で「1着馬名(タイム差)」とのみ表記）
  - `/horse/{id}/` は競走成績テーブルなし、`/horse/result/{id}/` が別途必要
  - **推測実装していたら全馬 rank=undefined で片肺動作のまま発見遅延**
  → 案を `/horse/result/{id}/` 全頭叩きに切り替え、コミット 30bc455〜6264fea で完遂

- **2026-05-07: バックテスト時間整合性**:
  「過去レースの過去走を *現在* 取得すると未来情報が混入」（タイムリーキ）。
  100R バックテストは設計から見直しが必要となり別タスクへ分離。

- **2026-05-07: WEIGHTS 配分の前提崩壊**:
  Phase 2E Stage 3 の重み配分は「**courseRecord = 50 固定**」前提で導出されていた。
  courseRecord 実装で前提が崩れたため、Phase 2H として重み再チューニングが必要。

- **2026-05-09: レース名正規化のバグ発見** (commit 528ba12):
  - 推測実装の落とし穴: 下調べで「条件戦の括弧表記 (1勝クラス)」だけ確認して
    「重賞も同じ慣習」と過度に一般化。`\([^)]*\)` で全括弧を一括削除する正規化を実装。
  - 結果: `天皇賞(春)` と `天皇賞(秋)` が同一視され、本来別レースの実績まで
    重賞前年補正の対象になっていた。
  - 回避できた理由: 本番動作確認 (`verify_production_run.ts`) の実 netkeiba 取得で
    「15/15頭が前年同名レース所有」という異常値を見て即座に検知。
  - 教訓: 「設計時に思いつく代表例 (条件戦)」だけでなく「実データに存在する全パターン
    (春/秋/コース別/距離別の意味的括弧)」を実機で確認する必要がある。

- **2026-05-09: タイムリーキ第二バグ発見** (commit 3801986):
  - 推測実装の落とし穴: 「過去走テーブル ≡ 過去レースのみ」と暗黙に仮定し、
    `/horse/result/{id}/` が事後収集される構造上「検証対象レース自身」や
    「baseDate より未来のレース」まで含むことを考慮しなかった。
  - 結果: 検証対象自レース (2025/5/4 天皇賞春) や、それより未来 (2026/5/3) のレースが
    「過去走」として補正対象に混入。norm 修正後も「15/15頭」が解消しなかった。
  - 回避できた理由: 1件目のバグ修正後の **再実行による検証** で異常継続を発見。
    `if (d >= baseDate) continue;` 追加と `parseRaceDate(race.raceDate)` 優先で
    完全解消 (15/15 → 3/15 に収束、馬3/12/13 のみ正当な前年実績保有として残った)。
  - 教訓: 「修正した = 直った」と決めつけず、再実行で必ず検証する。**複数バグが
    同じ現象を引き起こしている可能性**を常に疑う。1件目を見つけても2件目以降を
    探し続ける姿勢が必要。
  - メタ教訓: 対話役が「これが原因」と早期断定すると第二バグの発見が遅れる。
    実装側 (CLAUDE.md ルール) で「再実行検証」を制度化することで救済された。
