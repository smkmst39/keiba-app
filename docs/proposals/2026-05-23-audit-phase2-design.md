## 1. jockey 急変が事前検知できなかった理由

### フェーズ1 (AUD-1〜4) の限界
| 監査項目 | 検知できたか | 理由 |
|---|---|---|
| AUD-1 distinct 値数 | 🔴 100% 発症で初検知 | 「現時点で異常か」のスナップショット |
| AUD-2 50占有率 | 🔴 100% 発症で初検知 | 同上 |
| AUD-3 lastThreeF=training | ⚠️ 別問題 | 旧ロジック残存の検知 |
| AUD-4 pastRaces 保存率 | ✅ 0% で即検知 | スナップショット |

**全項目が「現時点」のスナップショット監査**。前回レポートとの差分を取らないため、`9.3% → 30% → 80% → 100%` の急変過程が見えない。

### 急変過程（再掲）
```
2026-04-04 〜  0.1% (健全)
2026-04-05 〜 26.5% (急変開始) ← ここで検知できれば3週間早く対処可能
2026-04-18 〜 36.2%
2026-04-25 〜 82.6%
2026-05-02 〜 100% (完全発症)
```

→ **過去レポートとの差分があれば 2026-04-05 で警告を出せた**はず。

## 2. 設計の基本アーキテクチャ

### 既存リソース (フェーズ1 で確立済)
- `scripts/audit/reports/audit_YYYYMMDD.json` (機械可読、各回ごとに蓄積)
- 既に 5-23, 5-24, 5-27 の3回分が蓄積されている
- 各レポートは `bAll` / `bRecent` の構造化集計を持つ → そのまま比較可能

### 急変検知のアーキテクチャ案

#### 案A: 直前レポートとの差分（推奨）
- 最新レポート N と N-1 を読み込み、各メトリクスの差分を算出
- 閾値超過なら警告
- **メリット**: 実装が単純 (~50行)、過去レポートが蓄積されていれば即動く
- **デメリット**: 1週間で急変したケース (今回はちょうど合う) には強いが、3ヶ月かけて緩やかに悪化するケースには弱い

#### 案B: 過去N回の移動平均との差分
- 直近4週の移動平均と最新値を比較
- ノイズ耐性が高い
- **メリット**: 緩やか悪化も検知できる
- **デメリット**: 実装やや複雑、初回起動から4週は機能しない

#### 案C: 全履歴と最新の比較
- 過去全体の平均と最新値を比較
- **デメリット**: 古いデータが多くなると感度が下がる。長期悪化を当たり前と見なしてしまう

### 推奨

**案A を採用、将来 案B へ拡張**。今回の jockey ケースは 1週間で 0% → 26% の急変であり、案A で十分検知できる。緩やか悪化への対応は実運用で必要になったら案B 追加。

## 3. 追加監査項目の候補仕様 (AUD-7〜9)

### AUD-7: 時系列急変アラート (推奨度 ★★★)

```
対象: components 各要素の 50占有率 / distinct 値数
比較: 直前回レポートとの差分 (案A)
基準:
  - 50占有率の差分 > +10pt → ERROR (急激な悪化)
  - 50占有率の差分 > +5pt  → WARNING
```

- 今回 jockey は 0% → 26.5% (差分 +26pt) で発症 → 閾値 10pt なら確実検知

### AUD-8: スクレイパー HTTP 取得成功率 (推奨度 ★★★)

R-1 で stats.ts に追加した `[stats] HTTP OK / HTTP失敗` ログを集計。

```
対象: 直近 collect.log の "[stats] HTTP" 行
集計: status=200 / 4xx / 5xx / 例外 の件数
基準:
  - status=200 比率 < 95% → WARNING
  - status=200 比率 < 80% → ERROR
  - 例外 > 10件/レース    → WARNING (ネットワーク不安定)
```

**根拠**:
- 今回の jockey 発症は HTTP 失敗が継続発生していたはず (仮説B 最有力)。これを集計していれば 100%発症前に「成功率 50%」段階で警告が出せた

**実装方針**:
- `scripts/audit/checks/scraper_log_parser.ts` 新設
- `scripts/verification/collect.log` を tail で読み込み (artifact からダウンロードしたものも可)
- 正規表現で `[stats] HTTP OK` と `[stats] HTTP失敗` の出現回数をカウント

**前提**: R-1 で stats.ts のログ強化が完了している (✅ 2026-05-28 完了)。

### AUD-9: 環境差分検知 (推奨度 ★★)

ローカル収集と Actions 収集で同一要素の分布が異なる場合を警告。

```
対象: components の値
集計: 直近 N 件を「収集環境 (ローカル / Actions)」でグループ化し、50占有率を比較
基準:
  - 同一要素の 50占有率が 環境間で >20pt 乖離 → ERROR
```

**実装上の問題**: verification JSON には「どの環境で収集したか」のフラグが無い。実装するには:
- (a) `predictions[].collectedBy: 'local' | 'github-actions'` を保存する型同期改修 (D-1 同様の軽改修)
- (b) ファイル名の prefix で推測 (週次スクレイプは火曜 = Actions、それ以外 = ローカル) → 不正確

→ **推奨度 ★★ にしている理由**: 実装に型同期が必要で、AUD-7/8 より重い。R-2 で原因確定後、必要性を再評価。
